ONE-TIME SETUP · FIREBASE + GITHUB PAGES

Connect your playbook.

The website already contains your crimson-playbook Firebase web configuration. Complete these steps in your Firebase console, then upload the updated website. You do not need to move your website off GitHub, install a server, or manually enter the 25 plays.

Use Cloud Firestore for this setup, not Realtime Database. The application uses Firestore and Firebase Authentication. Cloud Functions, Storage, Analytics, and a paid upgrade are not required for this design. Usage remains subject to your Firebase plan’s quotas.

How this compares with SQL

SQL termFirestore equivalentOur example
TableCollectioncoaches

ColumnField inside a documentfirstName, lastName, enabled

Database permissionsFirestore Security RulesOnly administrators can change selections and coach records

You do not need a CREATE TABLE statement. Firestore creates a collection when its first document is saved. Documents can include arrays, so this small app stores the selected play slugs together in one document rather than creating a join table.

1. Create the Firestore database

  1. Open the crimson-playbook Firebase project.
  2. In the left menu, open Build → Firestore Database, then choose Create database.
  3. If an edition is offered, choose Standard edition. Use the database ID (default). If this database already exists, use it instead of creating another.
  4. Choose a suitable US region. Check the choice before continuing; the database location cannot be changed later.
  5. Choose Production mode if asked about rules. We will supply the specific rules next. Do not use open test-mode rules.

2. Publish the supplied database rules

  1. Open the Rules tab in Firestore Database.
  2. Open firestore.rules from this package and copy its complete contents.
  3. For a new database dedicated to this playbook, replace the editor’s contents with that file, then click Publish. If your database already serves another app, merge its rules with these instead of overwriting them.

The team can read the current selection. Only a named administrator can write it. Coach names are private to administrators. Knowing a coach PIN never grants permission to change database records.

3. Enable administrator sign-in

  1. Open Build → Authentication → Get started.
  2. Under Sign-in method, enable Email/Password. Email-link sign-in is not needed.
  3. Open Users → Add user. Enter your real administrator email and a password you choose. Keep that password private; do not put it in your website files.
  4. After creating the user, copy its User UID. This long identifier is used in the next step, not your email address.
  5. Under Settings → Authorized domains, add the hostname of your GitHub Pages website, for example YOUR-USERNAME.github.io. Enter only the hostname, without https:// or a repository path. Add your custom domain too if you use one.
  6. For local testing, add localhost and 127.0.0.1 if needed. New Firebase projects may not include localhost automatically.

Coaches do not need Firebase Authentication accounts. Their PIN-only convenience access is managed in the website’s admin page.

4. Make that account an administrator

  1. Return to Firestore Database → Data.
  2. Click Start collection. Set Collection ID to exactly admins.
  3. For Document ID, paste the User UID from step 3. Do not use Auto-ID for this record.
  4. Add a field named enabled, choose type boolean, and set it to true. It must be a boolean, not the string “true”.
  5. Click Save.

The resulting path is admins/YOUR-USER-UID. This is the only application document you must create manually. The Firebase console can create it even though the website is prohibited from granting administrator access.

To add another administrator later, repeat steps 3–4 for that person. To revoke administration, change their enabled field to boolean false.

5. Upload the updated website

  1. Extract the latest crimson-playbook.zip.
  2. Upload the contents of its crimson-playbook folder to the same GitHub folder you already publish. Preserve the subfolders. Do not create another nested crimson-playbook folder.
  3. For this update, replace the root index.html, all play-folder index.html files, coach-guide/index.html, and the entire assets folder. Add admin/, firebase-setup/, and firestore.rules. Keep the supplied source files, build script, and README for future maintenance. Uploading the whole clean package is easiest.
  4. Wait for GitHub Pages to finish publishing, then press Ctrl+Shift+R on the live site.

Publishing the firestore.rules file to GitHub does not apply the rules to Firebase. Step 2 is separate and required. Weekly selections and PIN changes do not require GitHub uploads after this initial installation.

6. Choose the team’s plays

  1. Open your website and click Admin at the top.
  2. Sign in with the administrator email and password from step 3.
  3. Enter a heading such as “Week 3: spacing and help defense” and an optional message to the team.
  4. Check the drills and plays to display. Click Save team selection.
  5. Click Preview Team View. Confirm that only the checked plays appear. Players see changes when they open or refresh the page.

Saving automatically creates settings/team. An empty selection intentionally shows no plays; it never means “show everything.” If Firebase cannot be reached, the page shows a retry message instead of the complete library.

7. Add coaches and assign PINs

  1. In Admin, open Coaches & PINs.
  2. Enter the coach’s first name and last name. These are labels for you; coaches do not type them to sign in.
  3. Assign a unique 4–8 digit PIN. Six or more digits is recommended. Leading zeros are preserved. Two coaches cannot share the same PIN.
  4. Keep Access enabled checked, then click Add coach. Share the PIN with that coach separately.
  5. The coach opens Coach View, enters only their PIN, and sees every play. Selected team plays carry a “Team pick” label.

Add more coaches using the same form; there is no small application-level coach limit. For changes, choose Edit / change PIN. Leave PIN blank to preserve it, or enter a replacement. Uncheck Access enabled to turn off that coach’s access. A PIN change invalidates the old PIN. Existing open pages are not forcibly closed; access is rechecked on the next page load or refresh.

Coach access stays in the current browser tab’s session for up to 12 hours. Exit Coach View clears it. PINs are never shown again or stored as readable text. If a coach forgets one, assign a new PIN.

The records you will see

Document pathPurposeCreated by
admins/{uid}enabled: true grants administrator rightsYou, once, in Firebase console
settings/teamHeading, message, selected play slugs, revision, update timeSave team selection
coaches/{auto-id}First/last name, enabled flag, derived credential identifierAdd/edit coach
coachAccess/{derived-key}PIN lookup containing a coach ID and enabled flag; no names or readable PINAdd/edit coach

A slug is the play’s folder name, such as five-out. Animations and coaching instructions remain in content/ on GitHub. Firebase stores only selections and access records. No indexes or play-by-play database imports are needed.

About the simple PIN gate

This follows your goal of keeping players focused. Static play files remain public on GitHub; Coach View is a convenience gate, not a private content vault. A PIN is converted to a derived lookup key using PBKDF2 before checking Firestore. The rules prohibit listing those keys or reading the coach-name list publicly. Because this design has no custom backend, it does not provide server-enforced PIN attempt limits. Use it for this public playbook, not confidential player information. Administrator writes are protected separately with Firebase Authentication and Security Rules.

If something does not work

  • “Firebase blocked this request”: Check that step 2’s rules were published. For Admin, check the exact User UID document and boolean enabled: true.
  • Email/password sign-in not enabled: Complete Authentication → Sign-in method → Email/Password.
  • Unable to reach Firebase: Check the internet connection, the default Firestore database, and the project configuration. Run from HTTPS on GitHub Pages or a localhost server; do not double-click HTML files for this Firebase version.
  • No team plays: Open Admin, check plays, and save. This is expected before the first selection is saved.
  • PIN not recognized: Use only the PIN, including any leading zeros. Check that the coach is enabled. Assign a replacement PIN if necessary.
  • Another administrator changed the selection: Reload Admin to get the latest selection before editing again. This prevents silently overwriting another admin’s saved work.
  • The old website still appears: Upload the full update, wait for Pages publishing, and hard-refresh. The new data lives in Firebase, but the new interface must first be uploaded.
